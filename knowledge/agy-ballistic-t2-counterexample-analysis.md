## 1. Контекст и постановка открытого вопроса

В публичной ветке симулятора участник «Повелитель» (#11600, #11613) выявил подтвержденный дефект детектора `ballistic_action` в `src/debrief.js`:
- При завершении проекта на шаге `advance` (например, месяц 6 для туризма) событие `completion` только что добавлено в журнал.
- Игрок еще не имел возможности совершить ни одного действия после завершения, однако `analyzeDebrief` уже возвращает `detected: true, severity: 'high'`.
- Это ложноположительное обвинение игрока в «баллистическом стиле» (*Ballistisches Handeln*), нарушающее принцип объективности Дёрнера.

В документе `docs/ai-agent-fix-ballistic-followup.md` Senior Integrator Codex зафиксировал структуру состояний:
- **$T_0$**: Завершение только что произошло, возможность последующего действия еще не реализована $\to$ `followup_pending` (нейтрально, `severity: 'none'`).
- **$T_1$**: Получен профильный отчет службы после события завершения $\to$ снятие ожидания (`cleared`).
- **$T_2$**: Возможность проверки пропущена $\to$ `outcome_unverified` (констатация положительного факта отсутствия отчета за $N$ месяцев/шагов).

### Открытый вопрос спецификации:
> **Когда именно должно наступать состояние $T_2$:**
> - Вариант А: Сразу после любого первого действия игрока в журнале после завершения в том же месяце?
> - Вариант Б: Только после перехода к следующему календарному месяцу (`game.month > completeMonth`)?

Ниже представлен формальный анализ вариантов с минимальными контрпримерами и формулировкой оптимального синтезированного правила.

## 2. Анализ вариантов и минимальные контрпримеры

### 2.1. Вариант А: Граница по любому первому действию того же месяца

**Формулировка правила**:  
Если в месяце завершения $M$ после события `completion` в журнал записывается *любое* действие игрока (`policy`, `project` или непрофильный `report`), проект немедленно переводится из $T_0$ (`followup_pending`) в $T_2$ (`outcome_unverified`).

#### Контрпример 1: Естественный порядок действий внутри одного хода (Multi-action Turn)
Рассмотрим стандартное поведение игрока в месяце завершения проекта $M = 6$:
1. Игрок видит сводку месяца 6: проект «Развитие туризма» завершен.
2. В казне наблюдается небольшой дефицит. Первым действием игрок балансирует бюджет:
   ```js
   game = applyPolicy(game, { taxRate: 12 });
   ```
3. Вторым действием в том же самом месяце 6 игрок запрашивает профильный отчет по туризму:
   ```js
   game = requestReport(game, 'tourism');
   ```
4. Игрок завершает месяц: `game = advance(game, 1)`.

**Дефект Варианта А**:  
Между шагом 2 и шагом 3 (после `applyPolicy`, но до `requestReport`) статус проекта по Варианту А ложно переключается в $T_2$ (`outcome_unverified`). Если игрок в этот момент открывает кабинет или советников, система сообщает о «непроверенном исходе», хотя игрок находился в середине своего хода и добросовестно запросил профильный отчет до перехода к следующему месяцу.

#### Контрпример 2: Пакетный запрос всех отчетов (`request-all-reports`)
В веб-интерфейсе `src/app.js` (строки 1537–1543) реализована стандартная кнопка «Получить все отчеты»:
```js
case 'request-all-reports': {
  let updated = game;
  for (const kind of Object.keys(reports)) {
    updated = requestReport(updated, kind);
  }
  commit(updated, ...);
}
```
Порядок ключей в `reports`: `finance`, `factory`, `housing`, `social`, `tourism`.  
Если завершился проект `tourism`:
- Первым обрабатывается `requestReport(updated, 'finance')`.
- Для `tourism` отчет `finance` является непрофильным действием игрока после завершения.
- По Варианту А в момент итерации по `finance` проект `tourism` кратковременно помечается как $T_2$, хотя в той же микросекунде будет вызван `requestReport(updated, 'tourism')`.

**Вывод по Варианту А**: Назначение границы $T_2$ на любое внутримесячное действие некорректно, так как игровой ход в симуляторе Лоххаузена квантуется **месяцем**, а порядок переключения слайдеров и кнопок внутри месяца является произвольным артефактом UI.

### 2.2. Вариант Б: Граница по переходу к следующему месяцу (`advance`)

**Формулировка правила**:  
Пока текущий месяц равен месяцу завершения (`game.month === entry.project.completeMonth`), проект остается в статусе $T_0$ (`followup_pending`), если профильный отчет еще не был запрошен. Переход в $T_2$ (`outcome_unverified`) происходит только тогда, когда время ушло вперед (`game.month > entry.project.completeMonth`), а профильный отчет так и не появился.

#### Анализ свойств Варианта Б:
1. **Согласованность с пошаговой природой модели**: Месяц в симуляторе Лоххаузена представляет собой единый интервал планирования. Решения месяца вступают в силу на расчетном шаге `advance`. До нажатия кнопки шага ход не закончен.
2. **Отсутствие ложных срабатываний**: Игрок может в любом порядке менять налоги, субсидии и запрашивать несколько отчетов — статус $T_0$ не будет преждевременно наказывать игрока, пока у него остается возможность запросить отчет в текущем месяце.
3. **Чистота минимального контрпримера #11600**:
   ```js
   let game = createGame();
   game = startProject(game, 'tourism', 'verification');
   game = advance(game, 6);
   // game.month === 6: статус строго T0 (pending), detected === false.
   game = advance(game, 1);
   // game.month === 7: месяц упущен без отчета -> статус T2 (outcome_unverified), detected === false (или информационный факт).
   ```

#### Краевой случай Варианта Б: Завершение на горизонте партии ($M = \text{horizon}$)
Рассмотрим сценарий с горизонтом 36 месяцев (например, `factory_crisis` или `tourism_dilemma`), где проект завершается ровно в месяце 36:
- В месяце 36 игра достигает финала: `game.month === 36 === horizon`.
- Вызов `advance` блокируется (`reachedEnd = true`).
- Если использовать наивное условие `game.month > completeMonth`, то проект, завершившийся в месяце 36 без отчета, навсегда остался бы в $T_0$ (`followup_pending`), так как месяц 37 никогда не наступит.

## 3. Синтезированное каноническое правило (Спецификация)

Для идеальной точности и отсутствия краевых дефектов правило перехода $T_0 \to T_1 \to T_2$ формулируется следующим образом:

### Математическая модель состояний проекта:

Пусть $i_{\text{comp}}$ — индекс события завершения проекта в `journal`:
$$i_{\text{comp}} = \max \{ i \mid \text{journal}[i].\text{type} = \text{'completion'} \land \text{matches}(\text{journal}[i], \text{project}) \}$$

Пусть $R_{\text{post}}$ — множество запросов профильного отчета, совершенных строго после события завершения:
$$R_{\text{post}} = \{ j \mid j > i_{\text{comp}} \land \text{journal}[j].\text{type} = \text{'report'} \land \text{reportKind}(\text{journal}[j]) = \text{expectedReport}[\text{project.type}] \}$$

Тогда статус проекта определяется однозначно:

1. **Если $|R_{\text{post}}| > 0$ $\implies$ $T_1$ (`cleared`)**:
   - Профильный отчет был запрошен после завершения (в том же месяце или позже).
   - Задержка закрыта, результат верифицирован.

2. **Иначе (если $|R_{\text{post}}| = 0$):**
   - **Если текущий месяц превышает месяц завершения** ($M_{\text{current}} > M_{\text{complete}}$):
     $$\implies \mathbf{T_2 \; (\text{outcome\_unverified})}$$
     Возможность проверки в месяце завершения была упущена; наступили последующие месяцы без профильного контроля. Количество упущенных месяцев: $\Delta M = M_{\text{current}} - M_{\text{complete}}$.
   - **Если текущий месяц равен месяцу завершения** ($M_{\text{current}} = M_{\text{complete}}$):
     - Если игра достигла горизонта ($M_{\text{current}} \ge \text{horizon}$):
       - При вызове финального ретроспективного анализа (`analyzeDebrief` по итогам партии) статус фиксируется как $\mathbf{T_2 \; (\text{outcome\_unverified})}$, так как партия завершена и новых ходов не будет.
     - Во всех остальных случаях (штатный ход партии):
       $$\implies \mathbf{T_0 \; (\text{followup\_pending})}$$
       Игрок находится в фазе принятия решений месяца $M$; ожидание открыто.

## 4. Требования к языку и нейтральности формулировок

В соответствии с канонами Дёрнера и решением координации, системная диагностика фиксирует **наблюдаемые факты**, а не приписывает игроку психологические ярлыки или мотивы:

| Состояние | Прежняя формулировка (с дефектом) | Новая нейтральная формулировка |
| :--- | :--- | :--- |
| **$T_0$ (`pending`)** | *«Баллистический стиль (Ballistisches Handeln). Высокая тяжесть ловушки.»* | **«Ожидает проверки исхода»**: «Проект завершен в текущем месяце %month%. Профильный отчет службы пока не запрошен. Окно наблюдения открыто.» (`severity: 'none'`, `detected: false`). |
| **$T_1$ (`cleared`)** | *«После завершенных проектов были запрошены профильные отчеты.»* | **«Исход проверен»**: «После завершения проекта запрошен профильный отчет (%reportName%, месяц %month%).» (`severity: 'none'`, `detected: false`). |
| **$T_2$ (`unverified`)** | *«Баллистический стиль... После N проектов не найден отчет.»* | **«Исход не проверен»**: «После завершения проекта (%projectLabel%, месяц %compMonth%) профильный отчет службы не запрашивался в течение %elapsed% мес.» (`severity: 'low'` или `'medium'`, нейтральное описание). |

## 5. Матрица тестовых сценариев (TDD Test Cases)

Для будущей реализации в `tests/debrief.test.js` предлагается следующий набор строгих тестов:

1. `test('T0: completion in current month without later actions is followup_pending and not high-severity trap')`:
   - `startProject(tourism)` $\to$ `advance(6)`.
   - Проверка: `ballistic.detected === false`, статус проекта `'followup_pending'`.
2. `test('T1: matching report in the same month after completion clears pending')`:
   - `startProject(tourism)` $\to$ `advance(6)` $\to$ `requestReport('tourism')`.
   - Проверка: статус `'cleared'`.
3. `test('Negative control: matching report BEFORE completion does NOT clear pending')`:
   - `startProject(tourism)` $\to$ `advance(5)` $\to$ `requestReport('tourism')` $\to$ `advance(1)`.
   - Проверка: отчет месяца 5 был до завершения; в месяце 6 статус остается `'followup_pending'`.
4. `test('Intra-month policy change does not trigger premature T2')`:
   - `startProject(tourism)` $\to$ `advance(6)` $\to$ `applyPolicy({ taxRate: 15 })`.
   - Проверка: пока месяц 6 не завершен вызовом `advance`, проект остается `'followup_pending'`.
5. `test('T2: advancing to month 7 without report triggers outcome_unverified')`:
   - `startProject(tourism)` $\to$ `advance(6)` $\to$ `advance(1)`.
   - Проверка: в месяце 7 статус `'outcome_unverified'`, зафиксировано `unverifiedMonths: 1`.
6. `test('Edge case: project completing at scenario horizon')`:
   - Завершение в месяце $H$ при горизонте $H$. Финальный дебриф корректно фиксирует непроверенный исход без падения.
7. `test('Attribution check: verification retains credit to Повелитель (#11600, #11613)')`:
   - Проверка наличия ссылки и атрибуции в документации и коде.
