# Спецификация универсального рекурсивного кайдзен-промпта для ИИ-агентов

**Автор**: `agy` (Antigravity Research Assistant / Domain Expert)  
**Дата**: 2026-09-11  
**Назначение**: Промпт для бесконечного автономного цикла непрерывных улучшений (Кайдзен) веб-симулятора Лоххаузена без изменения текста запроса.

---

## 1. Архитектурные требования к рекурсивному промпту

Чтобы промпт можно было отправлять агенту бесконечное число раз без деградации, галлюцинаций и разрушения проекта, он должен обладать свойствами **идемпотентности, самосинхронизации и жесткой селективности**:

1. **Самовосстановление контекста (Re-entrant Context Synchronization)**:
   - Агент не должен полагаться на «память чата». В начале каждого цикла он обязан программно считывать: `git status`, последние коммиты, входящую почту в `COORDINATION/mail/`, активные задачи в `COORDINATION/tasks/` и доску `TASK_BOARD.md`.
2. **Нулевой допуск к регрессиям (Zero-Regression Invariant)**:
   - Любая итерация начинается и заканчивается запуском полного тестового контура (`npm test`, `npm run check`, `verify-scenarios.mjs`, `verify-http.mjs`). Если в репозитории есть сломанный тест — единственная разрешенная задача агента: исправить регрессию (правило *Fix-First*).
3. **Кайдзен-фильтр ценности (Didactic Value vs Cosmetic Noise)**:
   - Запрет на «фичи ради фичи» (декоративные украшательства, бессмысленные слайдеры, усложнение моделей без дидактической нагрузки).
   - Каждое улучшение обязано отвечать на 3 вопроса:
     1) *Делает ли это скрытую динамику системы (задержки, петли, побочные эффекты) наглядной для игрока?*
     2) *Устраняет ли это конкретную когнитивную ошибку Дёрнера (баллистическое действие, капсулирование, забывание лагов)?*
     3) *Подтверждено ли изменение строгим тестом и детерминированным расчетом?*
4. **Атомарность шага (Single Atomic Increment)**:
   - Ровно одно законченное улучшение за цикл (исправление дефекта, калибровка порога, дидактическая визуализация, аналитический разбор или улучшение доступности). Не начинать несколько параллельных масштабных строек.
5. **Строгое соблюдение протокола координации**:
   - Не трогать чужие файлы без согласования, соблюдать роли (Codex — старший интегратор, agy/dorner_* — исследовательские и профильные компоненты), обновлять только свои статусы и `TASK_BOARD.md`.

## 2. Текст универсального кайдзен-промпта

```markdown
Ты работаешь в режиме непрерывного улучшения качества (Кайдзен) веб-симулятора Лоххаузена по книге Дитриха Дёрнера. Выполни строго одну итерацию Кайдзен по следующему регламенту и не останавливайся:

### ШАГ 1. СВЕРКА КОНТЕКСТА И ПРОВЕРКА ДРУГИХ АГЕНТОВ
1. Выполни `git status` и `git log -n 5 --oneline`.
2. Проверь новые письма в `COORDINATION/mail/<твое_имя>/` и почтовых ящиках коллег.
3. Прочитай актуальные задачи в `COORDINATION/tasks/` и обнови свой файл состояния `COORDINATION/state/`. Чужие файлы не перезаписывай.
4. Прогони полный проверочный контур: `npm test`, `npm run check`, `node scripts/verify-scenarios.mjs`, `node scripts/verify-http.mjs`.
   - ЕСЛИ хотя бы один тест упал: твоя ЕДИНСТВЕННАЯ задача на этот цикл — локализовать и устранить регрессию. Переходи к шагу 4.

### ШАГ 2. КАЙДЗЕН-АНАЛИЗ («КАК Я МОГУ УЛУЧШИТЬ ПРОЕКТ?»)
Задай себе 3 кайдзен-вопроса Дёрнера:
1. Какая системная связь, задержка или побочный эффект сейчас скрыты от игрока или искажены?
2. Какая когнитивная ловушка (баллистическое действие, привыкание к ползучему упадку, самооправдание задним числом, перерегулирование) не вскрывается текущим интерфейсом?
3. Что в кодовой базе, тестах, документации или локализации является неточным, вводящим в заблуждение или избыточным («фича ради фичи»)?

Выбери ОДНО наивысшее по пользе атомарное улучшение из системного бэклога (`TASK_BOARD.md`, замечания Codex или свежие аудиты).

### ШАГ 3. РЕАЛИЗАЦИЯ В СВОИХ ГРАНИЦАХ
- Строго соблюдай границы записи (не модифицируй файлы, находящиеся на интеграции у других участников, без явного ACCEPT в почте).
- Если улучшение затрагивает логику/UI: используй TDD (сначала напиши падающий тест `RED`, затем реализуй `GREEN`, затем сделай чистый `REFACTOR`).
- Если улучшение научно-дидактическое: оформи точный математический расчет, кейс-стади или спецификацию в `knowledge/` со строгими формулами и ссылками на первоисточники книги.

### ШАГ 4. ПОЛНАЯ ВЕРИФИКАЦИЯ
1. `npm test` — все тесты обязаны быть 100% зелеными.
2. `npm run check` — 0 синтаксических ошибок.
3. `node scripts/verify-scenarios.mjs` — 720 месяцев без сбоев балансов.
4. `node scripts/verify-http.mjs` — 12 страниц и 13 модулей отдают 200 OK.

### ШАГ 5. ФИКСАЦИЯ И ОТЧЕТ
1. Обнови `TASK_BOARD.md` и свое состояние `COORDINATION/state/`.
2. Если нужно согласование с коллегами — отправь точное письмо в `COORDINATION/mail/`.
3. Сформируй краткий итоговый отчет пользователю:
   - **Что улучшено в этой итерации**: суть изменения и его польза для пользователя.
   - **Какую системную ошибку/ловушку Дёрнера это устраняет**: дидактический смысл.
   - **Результаты проверки**: статус тестов и сценариев (например, 95/95 green).
   - **Следующий кайдзен-шаг**: что намечено на следующую итерацию.
```

## 3. Почему этот промпт работает бесконечно?

1. **Он самобалансируется**: В начале каждого запуска агент сам читает актуальную файловую систему, а не галлюцинирует старый диалог. Если другой агент добавил фичу или тест, промпт автоматически это подхватывает.
2. **Он предотвращает поломки**: Шаг 1 и Шаг 4 образуют непреодолимый защитный барьер: ни одно изменение не считается завершенным, пока не пройдены все 95+ тестов и сценарии.
3. **Он направляет творчество в русло науки, а не хаоса**: Вопросы шага 2 фильтруют любые попытки нагородить случайных кнопок, заставляя фокусироваться на петлях обратной связи, задержках и осознании ошибок игроком.
4. **Он готов к циклическому вызову**: Команда завершается структурированным отчетом и ясным указанием следующего шага, делая систему готовой к немедленному повторному перезапуску.
